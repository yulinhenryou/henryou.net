# henryou.net

## Scope and implementation
- Incrementally edit this existing HTML/CSS site. Read README, HTML, CSS, git status, branch and remote first; preserve unrelated/uncommitted work.
- Static document root is this repository root. Keep the existing GitHub → Cloudflare Pages deployment (`main`, no build command, output `.`). Do not change hosting, DNS, domain or Git history without an explicit request.
- White background, black text, subdued readable dates; single column, left aligned, 45rem (720px at default settings) homepage width; articles use a 720px body and centred date/title header. Baskerville first, Songti SC/Noto Serif CJK SC for Chinese, then Georgia/serif. No external fonts or copied system fonts.
- Keep the current identity layout, portrait/CV placeholders or supplied replacements, email, social URLs, identity introduction and About wording unchanged unless specifically requested.
- No client JavaScript, frameworks, build system, CMS, database, tracking, navigation bars, cards, decorative effects or invented content. Share `style.css` across all pages. Increment its query version consistently when CSS changes.

## Content
- Homepage order: About → Experience → Projects → Updates. Omit Projects/Updates entirely when empty, including archive links. Templates live in README, not public sample pages.
- Experience: one `.experience-entry` per real entry, newest start date first. Combine education/internships/research/work; date, optional 32px `.institution-logo`, then `.experience-detail`. Use uncropped `object-fit: contain`; remove the image element if absent. Never invent credentials or dates. Henry has chosen no institution logo for now; do not add one without a new request. Record official logo source and known usage requirements in README before adding a local asset under `assets/logos/`.
- Projects: `.project-list` with name, one factual sentence and only verified Code/Demo/Write-up links. No fake `href`, repository scraping or duplicate internship records. Create `projects/<slug>/index.html` only if a real project needs a detailed account.
- Updates (display name only): real HTML directories at `writing/index.html` and `writing/<stable-slug>/index.html`, created with the first real publication. Use the README templates. Homepage shows at most the five newest published entries without an All updates link; archive lists every published entry in descending publication-date order. No excerpts, categories or other metadata.
- Articles: UTF-8, correct `lang` (`en`, `zh-Hans`, etc.; mark language changes when useful), accurate title, canonical URL, semantic article/header/time/body, simple back link. Use supplied date or actual publication-day date in Australia/Sydney; `datetime` is YYYY-MM-DD. Keep URL and original publication date on revisions, even if the title changes. Investigate slug collisions before writing.
- Shared article typography: use `.article-page`, `.article-header`, `.prose` and README markup; date followed by an Updates archive link in a centred `.article-meta` row above the title (no top-left article link), 36–56px responsive title, 20px body (18px mobile), 1.75 line height, 24px paragraph and 32px figure spacing. Keep the body left aligned and photos consistently full-column width at a 3:2 display ratio through `.photo img` and proportional centre cropping. Use large enough sources; omit or replace undersized photos. Check subjects remain visible; retain uncropped diagrams/screenshots in plain figures. Apply changes through shared CSS for all future articles.
- Images: local `assets/writing/<slug>/`, preserve intrinsic proportions (no stretching) and relevant in-text position, meaningful alt text, figure/figcaption only for genuine captions. Optimise without blurring text and remove unnecessary location/privacy metadata. Use `.table-scroll` with `tabindex="0"`, `role="region"`, an accessible name and a real table/caption for wide tables; make overflowing `pre` keyboard-focusable too.

- Homepage typography: `.home` scopes compact list rules away from `.prose`. Use shared spacing variables, three 1px #e5e5e5 borders only between adjacent home sections, 32px above/below each border (24px mobile), heading-to-content 24px (20px mobile), About paragraph gaps 16px, item-internal gaps 8px, separate entries 32px, update rows 12px. No extra bottom margins.
- Homepage sizes: regular headings 28px/26px, body 20px/18px at 1.6, institution/project names 20px, dates and resource links 16px. Lengths use rem; mobile gutters 20px. Share date width 7.5rem and gap 1.5rem between Experience and Updates; stack below 600px. Preserve Baskerville and actual user content.
- Keep `/writing/`, stable article paths, `#writing` and `#writing-heading` compatible. Only visible section labels change to Updates; do not globally rename internal classes/paths. No added All updates link.

## TXT / Word editing and publication
- Fully read the original. For DOCX, use the documents skill to inspect text, image placement/order, captions, tables, formulas and revisions. Explicitly report anything not reliably understood; never silently omit it.
- Default editing: necessary wording improvements, deduplication, paragraphs and web formatting only. Preserve voice, language, opinions and uncertainty; do not expand into tutorials, marketing or declarations, or invent facts/sources/quotes.
- Extract images from the original; do not ask the user to do this or require Markdown. Produce clean semantic HTML, not Word-export markup, screenshots of entire articles or embedded PDFs. No general-purpose import tool or third-party conversion upload.
- Keep original TXT/DOCX, private drafts, comments, temporary images and QA fixtures OUTSIDE both repository and served/deployed root (e.g. a dedicated `/tmp/henryou-*` directory). Do not rely on absence of links or on gitignore to protect served files. Only final authorised HTML and public assets belong in the site.
- “看看 / 润色 / 做草稿” means edit and local preview only. “发布这篇 / 编辑后直接上线” authorises checks then the existing GitHub → Cloudflare flow, without approval for every formatting choice. Ask together about unclear facts, material meaning changes or obvious privacy concerns.
- Preview-only requests require deployment confirmation before committing/pushing to production. Once authorised, update archive + homepage, inspect the staged diff/file inventory, use ordinary commits/pushes, wait for successful deployment and verify the real public pages; a commit is not proof of publication.

## Checks before handoff / publication
- Compare preserved identity/About text and links against the pre-edit version. Ensure every entry/date/link is factual and all required content survived conversion.
- Inspect desktop and 320px mobile layouts, mixed Chinese/English, long titles/dates, images, lists, quotations and keyboard focus. No document-wide horizontal scroll; wide code/tables scroll within their own region.
- Check image loading, alt text, local references, UTF-8/lang/title/canonical, publication order and latest-five limit. No broken or placeholder links in rendered pages.
- Check git diff and actual static file inventory: no private drafts, originals, QA pages, fake content, scripts, dependencies or unrequested features. Confirm hosting configuration is untouched.
- Report untested areas honestly. A synthetic article fixture does not verify a real TXT/DOCX import. Keep preview screenshots outside the repository.
